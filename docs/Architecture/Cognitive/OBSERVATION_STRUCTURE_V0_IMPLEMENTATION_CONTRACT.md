## 1. Professional responsibility

Before a controller counts, sums, or compares any number in a financial file, they silently answer two separate questions about every row they look at: *"what role does this line play in the report"* (a raw entry, a subtotal, a headline indicator, a heading with no value) and *"was this number computed from other lines in this same file, or is it a source fact"* (because a computed line must never be summed alongside the lines it was computed from, on pain of double-counting). An excellent controller never confuses these two questions, even though a careless reading of the file often makes them look like the same question — this contract exists because Pepperyn made exactly that conflation in its first working draft of this capability, and a real row in a real file (Phidani, row 163) proved it wrong.

## 2. What v0 classifies — resolution of the three candidate questions

The founding question (mission §2) asked whether "structural role," "how the value was produced," and "is it an independent economic observation" are the same dimension, orthogonal, or should not all exist in v0. Resolved as follows, evidenced against real `Phidani.xlsx` rows (all row numbers below refer to the real file, sheet `PHIDANI`):

- **`structural_role`** — WHAT ROLE this observation plays in the report's own structure. Kept as a first-class v0 dimension.
- **`derivation_status`** — HOW the observation's value was produced, as observable from within this file. Kept as a first-class, **separate** v0 dimension.
- **"Independent economic observation"** — split in two on inspection, and **not** kept as a third v0 dimension:
  - *Arithmetic independence* ("is it safe to sum this into a total alongside other rows without double-counting?") is a pure, mechanical **consequence of `derivation_status`**, computed **fail-closed**: `derivation_status == SOURCE_VALUE` ⇒ arithmetically independent; anything else (`DERIVED`, `NOT_APPLICABLE`, **and, critically, `UNKNOWN`**) ⇒ not treated as independent. **Corrected 2026-08-10 (independent adversarial pre-implementation review):** the original text of this convenience formula read `derivation_status != DERIVED`, which would silently treat `UNKNOWN` rows — i.e. rows whose true nature is genuinely unproven — as safe to sum. On a no-formula-cached export (§6), *every* row's `derivation_status` degrades to `UNKNOWN`; a consumer applying the original formula would then treat the whole file as "safe," reintroducing exactly the rollup double-counting defect this capability exists to prevent. `NOT_APPLICABLE` is a moot case either way (no value to sum), but `UNKNOWN` is not — it must never be silently upgraded to "independent" by exclusion. No separate field is needed for this; a consumer computes it as `derivation_status == SOURCE_VALUE` if convenient.
  - *Analytical meaningfulness* ("is this a fact worth citing to a human as its own observation, regardless of whether it is arithmetically redundant?") is **not** determinable from structure alone (Phidani row 133, `"B1 Marge brute d'exploitation (EBITDA)"`, formula `=C35-C132`, is arithmetically 100% redundant with its two inputs yet is the single most citable number in the file) — this belongs to the future Economic Nature / Reporting Structure capability (#2/#3 in the profession-model document), explicitly **OUT** of this slice.

**Proof the two kept dimensions are genuinely orthogonal, not derivable from each other** (the founding tension named in the mission brief and in Fred's closing note): Phidani row 163 (`630`, `"D. Amortissements - Réductions Valeur"`, formula `=C162`) has `structural_role = AGGREGATE` (bold, lettered statutory caption, correct hierarchy position — the official "D." line of the Belgian minimum schema) yet `derivation_status = DERIVED` via a **trivial single-cell passthrough**, not a genuine multi-row sum — its role says "aggregate," its derivation mechanism looks nothing like the textbook "sum of many leaves" (row 161, `62`, `=SUM(C134:C160)`) that motivated the original model. Conversely, a hardcoded manual Excel total (mission §3 case 10, not present in Phidani, constructed conceptually) would show `structural_role = AGGREGATE` (from caption/position evidence alone) while `derivation_status = SOURCE_VALUE` (no formula observable in this file) — the mirror-image proof. Neither field can be reliably computed from the other; both are required.

**Scope unit — corrected 2026-08-10 (independent adversarial pre-implementation review):** both dimensions apply to a **row observation within one specific period column** — i.e. a `(row, column)` cell — not to "a row" as a row-level constant. `derivation_status` was already implicitly cell-scoped (FRU's adapter takes a `period_column` argument; a row can legitimately be `DERIVED` in one column and `SOURCE_VALUE` in another, e.g. a manually-corrected historical month). `structural_role` is *usually* stable across a row's columns (caption/position evidence doesn't change per column) but is not guaranteed to be — a row can be structurally KPI-shaped yet have `derivation_status = NOT_APPLICABLE` in one specific blank column without ceasing to be a KPI-shaped row (Phidani row 256, `"B3 XIII Résultat à affecter"`, blank in some period columns, is exactly this case — see §11's Golden Case and §12 fixture G). **The Golden Case table in §11 (header "Formula (col C)") and every fixture in §12 are implicitly scoped to one column; this was not previously stated explicitly and could mislead an implementer into treating either field as a row-level constant.**

## 3. v0 classification semantics

### 3.1 `structural_role` — four values, non-exclusive-in-reality but exclusive-by-convention in v0

| Value | Meaning | Real Phidani example |
|---|---|---|
| `LEAF` | A raw, individually-posted line — the smallest unit *this report shows* (never a claim about true upstream ledger atomicity — see honesty note below). | Row 134, `620250`, `"Rémunération brute employés"`, `863540.12`. |
| `AGGREGATE` | A subtotal/total line whose formula sums the **complete, contiguous set of sibling rows** beneath one hierarchy parent — a purely structural test, not a semantic one (see revised KPI test below for the contrast). | Row 161, `62`, `"C. Rémunérations..."`, `=SUM(C134:C160)` (sums every leaf between the previous and next lettered subtotal); row 165, `60/64`, `"II Coût Ventes-Prestations"`, `=C34+C132+C161+C163+C164` (sums *every* lettered subtotal — A, B, C, D, G — at the tier immediately beneath it, none skipped). |
| `KPI` | **Corrected 2026-08-10 (independent adversarial pre-implementation review):** the original wording — "a headline/management indicator" — was semantic, not structural, and directly contradicted §2's own exclusion of "analytical meaningfulness" from v0. Redefined structurally: a `DERIVED` row whose formula combines a **small number of specifically-named, already-`DERIVED` cells drawn from different hierarchy branches**, rather than the complete contiguous sibling-set beneath one parent (the `AGGREGATE` test above). This proxy is inherently imperfect — it cannot be computed with certainty without hierarchy-edge information this contract deliberately does not build (§10, `derived_from` deferred) — so `KPI` **can never be assigned at `STRONG_INFERENCE` tier in v0, only `HYPOTHESIS` or `UNKNOWN`.** | Row 133, `B1`, `"Marge brute d'exploitation (EBITDA)"`, `=C35-C132` — two named cells, not a sibling-closing range; `C35` and `C132` are themselves `DERIVED` ("derived from derived," §3.2). Contrast row 165 above, which structurally *is* a complete sibling-closure and is therefore `AGGREGATE`, not `KPI`, despite also combining several already-derived rows. |
| `SECTION_HEADER` | A row-level pattern (no code, no value in **any** period column, pure caption text) — never triggered by a single blank cell in an otherwise normal row (see §2's scope-unit note; contrast row 256/`B3`, blank in some columns, which stays `KPI`-shaped, not `SECTION_HEADER`). | Row 3, `"Compte de résultats"` (no code, no value); row 369, `"PASSIF"` (no code, no value). |

**Epistemic honesty on `LEAF` (added 2026-08-10, symmetric to `SOURCE_VALUE`'s existing caveat below):** `LEAF` means *"the smallest unit this file shows,"* never a claim that the figure is genuinely atomic upstream (mission §3 case 9 — a value an ERP already computed before export is, from Pepperyn's vantage point, indistinguishable from a true leaf). Same permanent epistemic limit as `SOURCE_VALUE`, stated here so a future consumer (#2) does not treat `LEAF` as a guarantee of ledger-level indivisibility.

**Compound-row decision (mission §3 test 7 — a row that is simultaneously a section boundary and carries a subtotal value, e.g. row 165, roman-numeral `"II"`, bold, formula-derived):** classified by its **value-bearing behaviour**, i.e. `AGGREGATE`, not `SECTION_HEADER`. The fact that its caption *also* marks a section boundary is real and useful but belongs to the future Reporting Structure capability (#3a in the profession-model document) — v0 does not attempt to represent "this row is both a subtotal and a section boundary" as a compound state. Named explicitly, not silently dropped.

**KPI-vs-AGGREGATE ambiguity is tolerated, not escalated (see §8 — no Epistemic Dialogue in v0):** distinguishing a sibling-closing statutory subtotal from a cross-branch headline figure sometimes depends on organisation-specific caption convention (Phidani's ad-hoc `"B0"`/`"B1"`/`"B2"`/`"B3"` code family, which is this report template's own invention, not a Belgian universal signal — flagged explicitly, never generalized) and, per the revised `KPI` test above, on hierarchy-edge information v0 does not build. Because both values carry the **same downstream consequence** (arithmetically not independent, per §2), v0 is permitted to return the coarser value or `UNKNOWN` role when the finer distinction is not resolvable, without blocking or asking a human.

**Invariant for the test contract (§16):** `SECTION_HEADER` must always co-occur with `derivation_status = NOT_APPLICABLE`. A classifier that ever produces `SECTION_HEADER` paired with `DERIVED`, `SOURCE_VALUE`, or `UNKNOWN` has a bug — this pairing is structurally impossible by both fields' own definitions (a pure-caption row has no value to have a derivation mechanism at all).

### 3.2 `derivation_status` — four values, evidence-graded

| Value | Meaning | Real Phidani example |
|---|---|---|
| `SOURCE_VALUE` | No formula observed in this cell in this file — *"no derivation evidence observable within this file,"* never a claim of true upstream non-computation (full caveat below; naming note: not to be confused with `financial_truth.py`'s unrelated `SourceType`/`SourceReference` vocabulary, which describes provenance *within Pepperyn's own pipeline*, not Excel formula mechanics). | Row 134, `620250`, `863540.12` (literal). |
| `DERIVED` | A formula is present in this cell, referencing other cell(s) in this file — regardless of whether it references one cell (row 163, `=C162`) or fifty (row 161, `=SUM(C134:C160)`), and regardless of whether the formula sums, subtracts, nets, or (conceptually, per §7) computes a ratio. **v0 deliberately does not sub-type the arithmetic operation** — sum vs. difference vs. ratio is an economic-nature/structure question (#2/#3), not an "is this safe to sum" question, and every one of those shapes has the identical downstream consequence. A formula present but evaluating to a blank/empty cached result is still `DERIVED`, not `NOT_APPLICABLE` — see the resolved edge case below. | Row 163 (`=C162`, single-reference); row 161 (`=SUM(...)`, multi-reference); row 133 (`=C35-C132`, difference of two already-`DERIVED` rows — "derived from derived," a real shape, not specially flagged as a distinct value). |
| `NOT_APPLICABLE` | No value **and no formula mechanism** present in this cell at all — a distinct state from `UNKNOWN`, because no derivation question even arises when there is nothing to derive. | Row 3 (`"Compte de résultats"`, no value in the value column); a blank future period cell (e.g. an October 2019 cell in a file that stops at September). |
| `UNKNOWN` | A value is present, but this file offers no formula-mode evidence for how it was produced (see §5's parser gap) and no fallback was attempted (see §6, §9 — no fabricated fallback). **Must be treated fail-closed by any consumer needing arithmetic safety (§2) — never silently treated as equivalent to `SOURCE_VALUE`.** | The conceptual no-formula-export adversary (mission §8) — not present in Phidani, which is 100% formula-consistent for every sampled subtotal. |

**Epistemic honesty on `SOURCE_VALUE` (mission §3 case 9, direct answer):** `SOURCE_VALUE` means *"no derivation evidence is observable within this file,"* never a claim that the number was not, in reality, computed somewhere upstream (an ERP module, a prior spreadsheet). Pepperyn cannot see past the boundary of the file it was given — this is stated as a permanent epistemic limit of this classifier, not a gap to close.

**Resolved edge case — formula present, blank cached result (added 2026-08-10, independent adversarial pre-implementation review):** a cell whose period column holds a formula (`is_formula = True`, §5) but whose cached numeric result is blank/`None` classifies as `DERIVED`, not `NOT_APPLICABLE`. Rationale: `derivation_status` is a claim about *mechanism* (is a formula the production method for this cell), not about the mechanism's current output — `NOT_APPLICABLE` is reserved for cells with no formula and no value at all (§3.2's own definition, "no value and no formula mechanism"). This does not weaken §5's "formula presence is the only signal" claim — the signal remains `is_formula`; this note only resolves which of the two "no visible number" states (`NOT_APPLICABLE` vs. a blank-result `DERIVED`) applies when they could otherwise be confused.

**Zero and absence stay distinct (Article III, extended here):** a literal `0` value is `SOURCE_VALUE`, not `NOT_APPLICABLE` and not `UNKNOWN` — a true zero is a fact, never confused with "nothing here."

## 4. Row / column scope — v0 is row-axis only, by evidence, not by symmetry

The profession-model document broadened the underlying problem to both axes (row aggregates *and* the real file's `"YEAR YYYY"` column aggregates). This mission confirms the **two-dimension vocabulary is axis-agnostic in concept** — `derivation_status` for a `"YEAR"` column is exactly the same kind of fact (does this column's value derive from other observations, here other *columns* of the same row, rather than other *rows* of the same column) — but the **evidence is not symmetric across axes**: `SECTION_HEADER` was observed only on the row axis (no column in Phidani carries "no value, pure caption" the way row 3 or row 369 do); a column-level `KPI`-equivalent (a variance or percentage column) is plausible but was not observed in Phidani at all (the file has no budget/forecast columns, confirmed in the profession-model mission). Per mission §5's explicit instruction not to force symmetry: **v0 implements the row axis only.** The vocabulary (`structural_role`, `derivation_status`) is deliberately defined generically enough (§3's wording never says "row") that a future column-axis extension would reuse it rather than redesign it — but that extension is explicitly deferred, not built now.

## 5. Deterministic evidence hierarchy — and the one real implementation gap

In decreasing reliability, as actually available today:

1. **Formula presence in the observation's own cell** (`derivation_status`'s primary and, in v0, only signal) — proven reliable across every sampled real-file row this and the prior mission inspected. **Requires `openpyxl.load_workbook(path, data_only=False)`** — formula-mode access.
2. **Caption/position/hierarchy evidence** (`structural_role`'s primary signal set) — section-title-row detection (no code, no value → `SECTION_HEADER`), bold/`outline_level`/indentation as corroborating-but-not-independently-reliable signals (row 231, `"650 A. Charges Dettes"`, is a genuine formula-derived subtotal with `bold=False` — proving bold alone is not trustworthy), account-code presence/absence and caption text pattern (lettered/roman-numeral captions) as weaker, Belgian-schema-flavoured corroboration.
3. **Formula reference extraction** (which cell(s) a `DERIVED` observation's formula points to) — cheaply available via the same regex-based approach `fru_sign_convention_detector.py` already uses for its margin-subtraction pattern search. **Not exposed as a v0 output field** (see §12 — no current consumer), but the extraction mechanism is a trivial byproduct of computing `derivation_status` and should not be thrown away if computed in passing.

**Signals technically observable but not currently used by anything, named per mission §6's explicit instruction not to silently omit them:** merged-cell ranges (`ws.merged_cells.ranges`); row-level `bold`/`outline_level`/indentation (present and informative in Phidani per the profession-model mission's inspection, currently read by nothing).

**The one real, currently-existing implementation gap (mission §6, §9 — must be named, not silently assumed solved):** the shared production Excel parser, `backend/services/file_parser.py`, reads files with `openpyxl(..., data_only=True)` as its **primary** strategy — i.e. it reads cached formula *results*, never formula *text*. Its documented last-resort fallback (plain pandas) reads "formulas as strings" only in a degraded path, unreliable as a primary signal source. **Formula presence is therefore not observable today from the shared, general-purpose file-ingestion pipeline that the rest of Pepperyn consumes.** It is observable only because `fru_sign_convention_detector.py`'s own adapter function independently re-opens the raw file a second time with a dedicated `data_only=False` call, coupled to a raw file path rather than to any shared parsed representation.

**RESOLVED (2026-08-10, "Observation Structure v0 — Formula Access Arbitration" follow-up mission — full findings not restated here, only the decision and its direct consequences for this contract):**

- **Decision: keep `file_parser.py` completely untouched; add one new, small, dedicated, shared formula-evidence module** (working name `formula_evidence.py` or equivalent, exact name an implementation-time detail) that performs **exactly one additional `openpyxl.load_workbook(..., data_only=False)` read**, exposing `is_formula` and `formula_text` (raw string, unparsed) keyed by real, unshifted openpyxl `(row, column)` coordinates — never the position-remapped row index `file_parser.py`'s DataFrame pipeline produces (that pipeline's `dropna(how='all')` and header-detection logic were confirmed, by tracing the runtime code rather than trusting its comments, to not reliably preserve raw sheet row numbers). This module needs **no** `data_only=True` companion read of its own — it never needs the computed value, only formula presence/text; any consumer that also needs the value (FRU) keeps getting it from wherever it gets it today, unchanged by this decision.
- **Why not modify `file_parser.py` itself:** its `_extract_sheets_openpyxl` already loses raw coordinates (by design — it produces an LLM-summarization-shaped, position-independent payload, not a cell-addressable one) and is consumed live by BFR/bilan-summary extraction, `temporal_normalizer` (via `_extract_temporal_headers`), and the EPM extractors (`financial_snapshot_extractor.py`, `business_health_extractor.py`, `metadata_extractor.py`) — threading formula metadata through that pipeline would require preserving coordinates end-to-end (a materially larger, riskier change) for a payload shape those consumers never asked for, and would still require a second `data_only=False` read internally regardless.
- **Why a single non-`data_only` read cannot serve both needs:** verified directly, not assumed — `openpyxl`'s `data_only` flag is fixed at `load_workbook()` time for the whole workbook object; a cell's `.value` returns either the cached numeric result or the formula string, never both from one loaded object. Confirmed empirically against real `Phidani.xlsx`: a `data_only=True` load and a `data_only=False` load of the same bytes agree exactly on every non-formula cell (row 134: `863540.12` both times) and diverge exactly as expected on formula cells (row 163: value `131323.73` vs. formula text `"=C162"`; row 231: value `28488.01` vs. `"=SUM(C174:C230)"`) — no discrepancy found. Each load took ≈2.0s on the real file; the two loads are independent costs, confirming "dual read" is a real, quantified, unavoidable cost of getting both payloads via `openpyxl`'s public API, not an implementation oversight.
- **No second source of truth:** the new module never produces or exposes a numeric value at all — `file_parser.py`'s cached-value output remains the sole canonical numeric representation for analysis/LLM purposes, completely unchanged. `derivation_status = DERIVED` is a claim about mechanism (a formula is present, as saved in the file), never a claim about whether the cached result is current — openpyxl cannot evaluate formulas or detect recalculation staleness, and this contract does not attempt to solve that (named as a permanent epistemic limit, same discipline as `SOURCE_VALUE`'s existing honesty language in §3.2).
- **Production risk today: effectively zero.** Tracing the live call graph (not assumed) found `fru_sign_convention_detector.py`'s workbook adapter, and therefore `epistemic_dialogue_service.py` (which imports only `Candidate`/`ABSOLUTE_POSITIVE`/`SIGNED_NATURAL` from it, never the detection functions), are **not wired into any router** — `routers/analyze.py` never calls `epistemic_dialogue_service`. Both are exercised only by their own test suites today. Adding the new module therefore changes zero live production behaviour; its I/O cost (≈2s on a Phidani-sized file) is paid only by whichever future consumer actually calls it, never by the majority-path analysis/LLM request flow.
- **Consequence for FRU:** out of scope for this decision — FRU's own existing `data_only=True` value-read is unchanged. A future (separately authorized) refactor could point FRU's formula-checks at the new shared module instead of its current inline `data_only=False` open, guarded by FRU's own existing, passing test suite (43 tests) — not performed here.

This resolves the blocker this contract originally left open. **Any v0 implementation of `derivation_status` now has a decided target design: the dedicated shared module above**, not an open choice between duplicating FRU's inline pattern per-consumer or waiting on `file_parser.py`.

## 6. No-formula case (mandatory, mission §8) — UNKNOWN is the correct v0 answer

Constructed conceptually — no real no-formula file was available. If every formula in Phidani were replaced by its computed value (a materialised/flattened export, or Case I/L from the adversarial matrices): `derivation_status` degrades honestly to `UNKNOWN` for every row that would otherwise have been `DERIVED` — there is no safe fallback signal in v0. Two theoretically possible fallbacks were considered and **explicitly rejected for v0**, per the mission's own "do not fabricate a fallback" instruction: (a) inferring structure from caption/position/ordering alone — this can still inform `structural_role` at `HYPOTHESIS` tier (independently of `derivation_status`, another proof the two dimensions are separable — §2), but cannot safely resolve `derivation_status`, since a leaf and a materialised rollup are visually and positionally indistinguishable once both are literal numbers; (b) an arithmetic cross-check (recomputing whether a candidate aggregate's value equals the sum of the rows structurally identified as its children, and inferring `DERIVED` if it matches) — a real, named, deferred idea (also named in the profession-model document's §16), not implemented here: no real no-formula file exists yet to calibrate against, and a false-positive cross-check match (a leaf value that coincidentally equals a plausible sum) would produce a confidently wrong classification, worse than an honest `UNKNOWN`.

## 7. Relationship to Evidence, FTE, FRU, Knowledge Model, Epistemic Dialogue

**Evidence** — no new evidence-capture mechanism needed. `structural_role`/`derivation_status` are new interpretive metadata about already-observed cells, shaped compatibly with existing `SourceReference` (sheet/row_label/period), but this contract does not require attaching them to `Evidence` — that is an extension decision for whichever consumer needs it (see §9).

**FTE** — no relationship; FTE operates on temporal column classification, entirely orthogonal to per-row structural classification.

**FRU (`fru_sign_convention_detector.py`)** — the **direct, proven, current consumer**. FRU's existing inline "structural rollup exclusion" (its own docstring's words) is, precisely, an unnamed, single-purpose implementation of exactly `derivation_status` — it already checks "is this row's period-column cell a formula" and excludes it from `charge_values` if so. FRU does **not** need `structural_role` at all — it only ever needed the `SOURCE_VALUE`/`DERIVED` distinction. This is named explicitly because it resolves §14's field-necessity test concretely: `derivation_status` has a real, live, already-implemented consumer; `structural_role`'s consumers (#2, #3) are future and not yet authorized.

**Knowledge Model** — **not needed by v0.** `structural_role`/`derivation_status` are near-fully deterministic per file (formula-mode evidence, when available, resolves them without needing organisational memory) and are re-derived correctly on every read — nothing here is worth remembering per Entity. Challenged directly (mission §12): could an organisation's *habit* of exporting with or without formulas be worth remembering, to pre-empt Case F/L's `UNKNOWN` degradation? Possibly, in principle — but this would be a memory about **the shape of an organisation's exports over time**, a distinct, future, terminology/pattern-flavoured capability (#5-adjacent in the profession-model document), not something Observation Structure v0 itself needs to persist or consume. **No new `SUBJECT_VALUE_REGISTRY` entry, no new KnowledgeModel subject.**

**Epistemic Dialogue — not needed by v0, deliberately.** The one plausible trigger (mission §13's own example: *"I cannot determine whether 'Operating Contribution' is a subtotal or an independent KPI"*) is directly answered by §3.1's tolerance rule: both candidate roles (`AGGREGATE`, `KPI`) carry the identical downstream consequence (arithmetically not independent, via `derivation_status` alone), so resolving the ambiguity with certainty is never required for v0's own purpose. **v0 remains fully deterministic, with `UNKNOWN`/coarser-role degradation as its only uncertainty behaviour — no human question is authorised or required by this slice.**

**`financial_truth.py` / `MetricType` — added 2026-08-10 (independent adversarial pre-implementation review), no relationship, named to prevent confusion.** `MetricType` (`REVENUE`/`GROSS_MARGIN`/`EBITDA`/`NET_PROFIT`/`COST`/etc., in `backend/models/financial_truth.py`) is a *semantic, LLM-populated, post-analysis* classification of an already-computed `QuantifiedImpact` — a different layer, different lifecycle stage, different (and currently dormant/legacy) pipeline than this contract's structural, pre-analysis, deterministic classification of raw cells. The two must never be conflated: `structural_role = KPI` (§3.1, corrected above to a purely structural test) says nothing about *which* economic indicator a row represents; `MetricType.EBITDA` says nothing about a row's formula shape. A single row (Phidani row 133) could legitimately carry `structural_role = KPI` here and, if it ever flowed through the unrelated `MetricType` pipeline, `MetricType.EBITDA` there — complementary facts, not competing ones, precisely because `KPI`'s definition no longer uses semantic language (§3.1). This mirrors the architectural-conflict item already named in `FINANCIAL_FILE_UNDERSTANDING_PROFESSION_MODEL.md` §13 (item 2) — restated here, not re-litigated.

## 8. Primitives future #2 (Economic Nature) / #3 (Reporting Structure) will need — not implemented here

Per mission §11 (do not implement #2/#3, but ensure v0 supplies the right primitives): future #2 needs to know whether a row is `LEAF` before attempting to classify its economic nature "as itself" (an `AGGREGATE`'s nature is derivative of what it aggregates — a different question). Future #3 needs the `SECTION_HEADER` boundary signal (§3.1) to reconstruct where one statement/section ends and another begins, and would benefit from the formula reference-extraction byproduct named in §5.3 (the parent/child edges a `DERIVED` observation's formula implies) to reconstruct hierarchy — **not exposed as a required v0 output field** (§12 — no current consumer), documented here only as a forward-compatible extension point so a future implementer does not have to rediscover it.

## 9. Downstream responsibility and persistence — challenged, rejected

Hypothesis tested (mission §9): is the classifier's output an ephemeral projection, deterministic metadata attached to Evidence, a persisted fact, or something else? **No case examined in this mission required persistence.** The output is a **pure, ephemeral projection** over a parsed workbook — recomputed fresh on every read, exactly like `fte_minimal.py`'s own precedent ("a pure projection over data that already exists... no new persistent object"). It may later be attached as optional metadata on a captured `SourceReference` if a future consumer needs traceability of the classification itself, but that is an extension, not a v0 requirement. **This classifier must never become a new canonical Evidence Ledger or a competing source of truth** — it answers a narrower, purely structural question than Evidence does, and produces no fact Evidence itself is responsible for capturing.

**Field-inclusion rule, stated once and applied consistently (added 2026-08-10, independent adversarial pre-implementation review — the three preceding rows previously carried separate, ad hoc justifications that could be read as inconsistent with each other and with §14's "no field without a current falsifiable need"):** a field is included in v0's output if EITHER (a) it has a current, proven consumer (`derivation_status` — FRU, §7), OR (b) it is a **free byproduct of computation §0-required for a field that already qualifies under (a) or (b)** — i.e. reading it costs no additional file access or parsing beyond work already being done (`structural_role`, computed in the same single row scan as `derivation_status`; `formula_text`, read from the same cell `is_formula` already inspects). A field that requires **additional** computation beyond what's already necessary — even if cheap in principle — does **not** qualify merely by citing a future consumer (`derived_from`, which needs formula-string parsing beyond the raw read, is deferred on this basis, not merely "no consumer").

**Confidence vocabulary:** both fields reuse the existing `FACT`/`STRONG_INFERENCE`/`HYPOTHESIS`/`UNKNOWN` tiers (`ConfidenceContract`, already canonical) — no new scoring engine, no fabricated numeric confidence, per Constitution Article XII (single representation) and the mission's explicit instruction (§15).
